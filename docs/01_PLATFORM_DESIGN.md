# VINS 单入口实验平台设计

更新日期：2026-10-28；状态：设计基线，v0.1 尚未实施

## Quick Start：希望用户怎样完成实验

新同学复制并编辑一份配置，后续只通过 `./vins` 操作。**下面 CLI 命令是待实现接口；当前只有复制模板和普通免密 SSH 已可用**

```bash
cp project.example.yaml project.yaml
# 编辑 project.yaml 中的数据、设备和实验参数
./vins run                       # 默认在板端播包，自动准备、部署、监控和回收
./vins run --host                # 相同配置在主机验证算法
./vins remote                    # 单独进入板端、自动激活当前包环境
```

另一个项目可复制为 `field.yaml`，统一使用 `./vins -c field.yaml run` 等命令；用户项目文件默认不提交。一般用户不需要手动启动 master、source 多份 ROS 环境或找多个配置文件

## 1. 目的、当前状态与本轮交付

工程服务于学生户外跑开环 VINS、录制原始相机/IMU 数据和回收实验结果。VINS 主体保持 C++，增加最少的构建、任务、传感器适配与观察能力；不以重写算法、远控协议或可视化平台为目标

本轮交付新分支、唯一配置模板、指导文档和新板子的探索证据。v0.1–v0.3 以下内容均为计划；不继续原生产分支的旧 v0.3，也不把历史包称为新平台产物

旧 ROS 1/ROS 2 最近共同祖先为 `5c575737e518351d0bc1abc3cdcdb11a96b8075d`，已经包含旧桌面基础设施；新分支从其之前的原生 `be55a937a57436548ddfb1bd324bc1e9a9e828e0` 建立。旧分支与全部 tag 保留只读参照，记录哈希，不删除或移动；本轮不打版本 tag

算法源码暂留根目录原生位置，避免为了目录整齐移动大量 C++ 文件。构建目标先限 `camera_models`、`vins_lib`、`vins_node`；回环、GNSS、KITTI、RViz 与硬件加速均不进入当前构建

## 2. 一个入口、一份参数来源

| 用户要做什么 | 计划命令 | 默认行为 |
| --- | --- | --- |
| 跑已有数据 | `./vins run` | 按配置自动检查、复用或构建包、部署、准备数据、启动、摘要监控及回收 |
| 主机验证 | `./vins run --host` | 同一算法和输入，在隔离 x86_64 环境执行 |
| 进入板端 | `./vins remote` | 固定工作目录，激活当前或活动任务使用的运行包 |
| 只推送包 | `./vins deploy` | 可续传、校验清单/依赖/权限/空间，成功后原子选定新版本 |
| 单独排查 | `./vins check` | 给出原因、路径和修复建议，不启动算法 |
| 查询进展 | `./vins status --follow` | 读取板端摘要；再次连接可接续查看 |
| 正常停止 | `./vins stop` | 请求板端落盘、清理本任务并按策略回收 |
| 断线后补收 | `./vins pull` | 按任务清单续传和验完整性，不重跑算法 |
| 开发者构建 | `./vins build --target board` | 显式准备 ARM64 运行包；普通 run 会复用同样流程 |

数据或包已匹配时 run 直接复用，失败阶段给出明确状态，不静默改参数重试。v0.1 默认每端一个活动任务；停止和补收默认选择当前/最近任务，存在歧义时显示具名列表，不要求用户手敲时间戳

`project.example.yaml` 是唯一可复制的根目录模板，默认 `project.yaml`，`-c` 可选择其他名字。路径相对于所选配置文件解析；编译依赖锁是开发者维护的来源清单，不是另一份日常实验参数

模板先覆盖播包所需：板端地址、工作路径、数据路径和回放范围、相机模型/尺寸/编码/内参/畸变、IMU 单位和话题、噪声、外参、时间偏移、特征与求解参数、监控、超时及回收策略。v0.2 再补真实设备的 SDK、序列号、串口、波特率、触发、曝光和录包等字段，不预先放无效配置

适配器生成本次 VINS 的 OpenCV YAML、标定文件和 ROS 参数，保存在任务目录并随结果归档，用户不编辑生成文件。模板使用 EuRoC 参数，不套用到当前真实相机；新场景应复制模板并修改相应数据和标定

原 `config/` 中其他设备、KITTI、仿真、RViz 及回环资源配置从当前分支清理，历史由原生提交保留。上游未读取的 `freq` 不作为可调算法参数；输出路径、相机数量等由受支持模式和任务目录生成，避免与模板形成两个来源

## 3. 语言与通信的取舍

建议先用 **uv 锁定的 Python 做薄编排，调用已成熟的 OpenSSH/rsync 二进制**；算法、驱动、必要的高频 ROS 观察用 C++。用户只看到 `./vins`，不暴露多组 `.py` 或要求安装一串命令

C++ 不会天然使文件传输、超时和进程清理更可靠；可靠性来自严格退出码、可恢复任务、清单校验和真实故障测试。先复用旧工具和 LIVO 平台中已验证的机制，按职责提取，避免复制整套代码；不新造 FastRPC、SSH 协议或常驻 RPC 服务

若后续确有“单个主机二进制、完全无需 Python”的交付要求，再评估冻结打包或薄 C++ 启动器，不让语言选型阻塞 v0.1 闭环。本轮未实现这一建议，远程工具最终形态可在 v0.1 开工时微调

传输使用 SSH 上的 rsync，显示总进度、速度和阶段，断线可续传；无 rsync 时检查明确报缺失条件，不在板端自动 apt。交互终端与自动任务共用身份、路径和环境；正式运行脱离交互 SSH，退出查看不停止任务，`stop` 才负责正常停止

## 5. 构建与运行包的环境解耦

主机完成两条独立构建：Linux x86_64 原生验证、Linux AArch64 交叉构建。两者使用同一源码、算法参数和依赖版本原则，隔离前缀、sysroot 与生成代码工具；host 工具与 target 库不能混用

| 依赖类型 | 管理和交付方式 |
| --- | --- |
| Python CLI/评估 | pyproject 与 uv.lock，锁定解释器需求和包；不污染系统 Python |
| OpenCV、Ceres、Eigen 及实际使用的非环境 C++ 依赖 | third_party 中固定来源，本机分别构建 host/ARM64，不能用未审计系统库顶替 |
| ROS、构建器和系统用户态基础包 | 独立环境/包版本锁，隔离提取或构建；必要运行库随私有包交付 |
| 相机/IMU 开源驱动与胶水 | third_party 可读源码加集中小补丁，交叉编译 |
| 闭源厂商 SDK | 固定官方目标架构产物，无法声称把不可获得的源码交叉编译；只编译适配器 |
| 内核、BSP、USB/UART 节点与权限 | 系统兼容条件，运行前检查；用户态激活脚本不能代替内核支持 |

uv 的锁定对象是 Python 项目依赖，不替代 CMake 的交叉工具链与 sysroot。构建器另锁系统/ROS/SDK 来源和校验值；用户体验仍是一条 run，而非要求用户维护多个工具环境。[uv 官方说明](https://docs.astral.sh/uv/concepts/projects/sync/)、[CMake 工具链说明](https://cmake.org/cmake/help/latest/manual/cmake-toolchains.7.html)

20.04 与 22.04 不应让用户重新搭环境：选择适合两者的基础 ABI 构建私有用户态包，检查所需 GLIBC/GLIBCXX、CPU 指令、动态库与 SDK 能力，再在声明支持的镜像上验收。当前板子 glibc 2.31 是兼容下限取证，不是必须使用系统 ROS 的理由；也不能据此直接复用旧 22.04 包宣称已兼容

包中至少包含 `env.sh`、统一运行入口、VINS/相机模型、私有 ROS 工具、实际依赖库、任务观察组件、资源、清单和来源。需要的 Python 运行时一并私有化；不把主机 venv 或 x86 安装前缀复制到 ARM

部署后 `source install/env.sh` 即可用包内程序。env.sh 只设置包内环境，不执行 apt/pip、厂商安装脚本、ldconfig 或修改系统 ROS。设备权限、USB 缓冲等不满足时在运行前明确指出；若需要一次镜像准备，必须单独列出，不伪称解压能解决所有内核/权限问题。当前板子的现有 USB/UART 权限已满足短时探索

检查 ELF 架构、依赖闭包、符号版本、可重定位路径、文件清单及校验值；新进程使用干净环境，不能 source 板端 `.bashrc` 后无意继承旧工作区。OpenCV/cv_bridge 必须同版本，不出现 4.2/4.4 混链

## 6. 一次任务及摘要监控

任务流程为检查 → 必要构建/部署 → 校验输入 → 私有 ROS master → 订阅就绪 → 数据源/算法 → 排空/停止 → 校验输出 → 回传。板端监督程序持有子进程、状态与清理责任，主机查看程序仅负责显示和操作请求

不在现场安装常驻服务。优先复用系统已有的临时任务管理；若使用 user service，须验证用户退出后能否存活，不能忽略当前 `Linger=no`。v0.1 要实际断开主机 SSH 验证；没有完整通过前不承诺断网独立运行

板端观察器以固定规则采样 ROS 话题、VINS 位姿和原文日志，每约两秒原子写出小型 JSON 摘要；主机轮询摘要，必要时增量读取已去重事件。字段包括任务/包身份、序号、阶段、观测单调时刻、各输入频率/计数/最新时间、位姿时间和位置、WARN/ERROR 类别/首次/末次/次数及进程状态

```text
[运行] campus-walk/001 | 图像 20 Hz | IMU 100 Hz | 位姿更新 10 Hz
[告警] IMU 实测与配置标称频率不同，详情已保存
[收尾] 数据源已结束，等待算法输出；不是“算法已完成”
[完成] 结果已校验并回收到 experiments/campus-walk/001
```

频率示例只说明显示格式。暂停、正常数据结束、设备断流、监控心跳失效和主机 SSH 断线分别建状态；快照陈旧时显示“观测过期”，不能用旧快照制造断流误报。算法没有输出时显示初始化尚未确认，不把节点存活等同正常定位

v0.1 观察图像格式/尺寸/时间、IMU 有限值与时间，以及位姿有限值/时间更新；只做必要格式和健康检查，不为完备性加入全部性能埋点。观察数不等于 VINS 实收/处理数；VINS 队列排空不能只凭文件大小稳定判断。必要的处理完成证据在实现时选择最小适配并明确仍未知的部分

原始日志保留板端，运行中不持续全量回传；结束后按配置压缩归档回收，失败也保留。大 bag/原始录包独立按策略传输。控制请求可重复，不能因 pull 或 status 再次启动任务；只停止本任务进程组，不做全系统 pkill

## 7. 版本与验收

### v0.1：通信、干净构建和一次播包闭环

范围：统一入口/配置、免密 SSH/交互环境、可见且可续传的部署与完整性检查、主机与 ARM64 构建、私有运行包、板端独立任务、主机摘要轮询、结果回收和开环单目 IMU 验证。先打通一个代表性任务，不先扩建插件平台

最小修复原生 `−6` 退出：参考旧 `fb4ad05` 的线程生命周期修复，仅提取必要源码改动，不合并旧平台。节点与后端库配套重建；正常停止、无输入、IMU 等待与完整回放都要退出正确，不能吞掉退出码假装成功

| 验收 | 必须看到的证据 |
| --- | --- |
| 初次使用 | 复制一份模板、修改数据路径、一条 run 完成；错误指出配置键、原因和路径 |
| 远控 | remote 进入正确目录/包环境；传输进度可见；损坏包、缺库和空间不足在启动前失败 |
| 可迁移 | 干净环境不读系统 ROS/全局 SDK/源码构建路径；换安装位置可运行 |
| 主机算法 | 固定 EuRoC MH_01_easy 单目 IMU 完整回放，轨迹/真值评估、末帧及进程退出可核验 |
| 板端算法 | 同一数据/配置完整回放，保存初始化、轨迹、时间覆盖、ATE/RPE 与退出证据 |
| 基线与补丁 | 同一目标旧/新最小退出修复串行对照；不要求跨架构轨迹字节相同，不以一次回放宣称实时 |
| 监控 | 频率/图像与 IMU 基本健康/位姿/WARN/ERROR 摘要可见；摘要失效单列；测观察开销 |
| 故障与恢复 | 断 SSH 后继续运行，重连 status/stop/pull；异常退出、超时、重复启动不遗留自有进程 |
| 完成闭环 | 数据结束后独立判断处理/停止，输出可读、有限、时间单调；清单校验回传一致 |

精度容差从固定协议的原生参照确定并写入验收记录，不预先捏造通过阈值；有尺度的 VIO 采用保持尺度的对齐。记录回放与排空时间、全线程 CPU、RSS/PSS、监控开销及板端温度，不以降低回放速度偷偷兑现实时性

### v0.2：真实单目相机与格纳威 IMU

只在主机交叉编译驱动与适配器，厂商 SDK 按目标架构打包；硬件验证直接在已接好设备的板端进行。沿用 run/任务/监控/停止/回收，不另建硬件工作流；可提供同入口 `record` 复用链路，只录原始数据而不强迫算法先成功初始化

模板扩充相机身份、像素格式、帧率、曝光/增益/触发、UART/波特率、驱动标称频率、时间来源、标定、录包分包与回收策略；这些信息只改一份。用户已说明 GNW 硬件实际约 100 Hz、旧驱动配置 200，先兼容并如实记录，不自动改硬件输出或因差异强制禁止原工作流

验收为一键部署后真实收数 → 开环 VINS 初始化并持续输出 → 正常停止落盘 → 原始 bag 与轨迹回传且能离线回放；直接用现场单目/IMU，不能套 EuRoC 标定。无真值只能证明运行与一致性，不能证明绝对精度；标定与时间同步质量单独标注

本版不新增一大套监控，不扩入 LiDAR、回环或旧共享内存预研。历史驱动只在妨碍当前集成时最小修补，保留原始来源和可复现证据

### v0.3：硬件驱动与户外采数健康

在已有摘要里补设备身份/访问状态、SDK 不完整帧/缓冲溢出、串口字节与校验失败、驱动存活/重启、实际采样率、设备/主机时间关系、曝光/触发有效状态、录包写入计数/磁盘余量及温度等可用信息；接口不存在就报告不可用，不用算法位姿推断设备一定正常

区分已观察、已写盘与算法已处理；监控自身失败要显式报告。掉线/恢复策略默认保守，是否重连后重置 VINS 依据输入连续性决定，不静默拼接不连续轨迹

验收覆盖相机/IMU 断流、驱动退出、磁盘空间不足、只断主机网线、监控失效及恢复；错误包含阶段、时间和设备/进程，已录数据尽可能可恢复。短时故障注入通过后再开展约定时长的户外实采，不能用软件演练代替真机稳定性

## 8. 实施顺序与以后再讨论的方向

v0.1 内先完成远程执行/任务身份/摘要和传输骨架，再完成 host/ARM64 构建和包，随后将两个环节串成一次完整回放；骨架到位后复用其入口验证，不长期手敲 SSH。每个小闭环独立提交，版本验收完成再打新的 annotated tag；不移动旧 tag，不把设计提交标成可用 release

更后面的批量回归、相机 IMU 标定辅助、离线回看、更细算法 profile、传感器同步和硬件优化仅为讨论方向。本轮不承诺 v1.0、不提前扩建数据库/网页/通用插件系统；以后由实际户外实验问题决定是否采纳
